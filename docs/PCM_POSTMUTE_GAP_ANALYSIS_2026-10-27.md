# PCM测试停止后心跳空档的只读分析

2026-10-27，仅分析已冻结的20261027-221627试次及相关源文件。本轮无硬件、网络、震动或固件操作，不改变映射、60ms接收策略、4ms请求休眠或80ms保护。原整轮INCOMPLETE不改写。

## 可核对的首次100.9062ms空档

故障快照保留了相邻两次原始有效接收及中间一次超时，记录中的gap与相邻接收时间差一致，未用缺失中间项的“匹配子集相邻”代替真正相邻。

| 阶段 | 时间 |
|---|---:|
| 上一帧有效接收→超时那次poll开始 | 11.5876ms |
| 该次poll调用直至返回超时 | 62.4941ms |
| 超时返回→下一帧有效接收 | 26.8245ms |
| 总有效接收空档 | 100.9062ms |

这些是应用层时间，poll调用包括输入读取、发送、接收和调度，不能叫纯无线往返或纯recv等待。

超时返回时距离80ms心跳线只剩5.9183ms。下一有效帧所属poll总耗时10.9856ms，但帧received_at在Client内部、外层duration结束在其返回后，因此只能得到下一poll起点下界：它至少在超时返回15.8389ms后开始，即至少晚于心跳线9.9206ms。下界不能写成精确起点，也不能把整个间隔认作sleep实测耗时。

这支持本次保护触发有实际的应用层空档依据；不能据此判定Wi-Fi掉包、Pico执行停顿、Windows某项机制或新增PCM摘要是根因。源码的collect_frames确实在每次poll后请求pause(0.004)，但当时没有分别记录pause进入/返回、观察层处理或线程调度耗时。

两有效回复的板端打戳差为92.161ms，PC取包差100.9062ms。它们是两次被接受回复之间的间隔，原请求号、发送时刻和原始/被丢弃旧回复均未保留；PC与板端绝对时钟未同步。不能把两间隔的差解释成单向链路时延或将板端间隔当作处理耗时。

## 最大135.9112ms的观测空缺

ObservedClient仅保留最近64次结果，并另外保存全局最大值和第一帧：

- 故障快照的64行覆盖PC时钟119.6425至120.7894秒，跨度1.147秒，含1次timeout；其全局及保留窗口最大间隔均为100.9062ms。
- 最终64行覆盖167.2951至168.2531秒，跨度0.958秒，保留窗口最大仅23.9623ms，无timeout。
- 两保留窗口之间约46.5057秒未保留逐次事件。最终全局最大值135.9112ms比首次快照更大，但两窗口均无对应行，无法恢复其精确时刻或原请求上下文。
- 最终4次poll超时不等于4个网络丢包；Client会过滤旧请求数据，当前元数据不含被过滤的数据报。

故障快照calls=9580、responses=9578、timeouts=1，余量1；最终13273=13269+4。快照函数没有锁、且calls在poll完成前递增，余量可能是进行中的poll或非原子读取，不能当丢包或计数损坏。只观察到一个启动标识，不新增设备重启结论。
