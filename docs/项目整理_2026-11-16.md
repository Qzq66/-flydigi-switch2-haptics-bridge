## 0. 一页结论

**已经做到的：**

- Switch 2 能识别 Pico 2W 模拟的 NS Pro 一代；
- 飞智按键、摇杆能经桥接正常转发；
- v043 完成 120 秒输入验收：`1969/1969`；
- 两轮 120 秒游戏闭环：`1107/1107`、`1120/1120`，各 25 项组合验收通过；
- 停止、CRC、序号、END2、原厂配置检查均通过；
- v043 固件已安装、读回、校验。

**2026-11-16 新增的关键事实：**

- 一条 Switch USB 触觉现场记录：设备以 `Pro Controller`（`057e:2009`）枚举，接受 `0x10`，8ms 端点，左右/两侧都能被感知，`162/162` 帧写出；
- 左握把的震动 consistently 比右侧钝，属于可复现的设备特性，不像传输/调度故障；
- 同一批工作还确认：飞智的蓝牙输入路线基本走不通——BLE 不广播，经典 HID 在认证阶段返回 `0x05`；
- 独立硬件方向明确为：Pico 原生 USB 做 NS2 设备端，PIO USB 做飞智接收器主机端。

**仍然不证明：**

- 原始 HD Rumble 2 的频率/幅度保真；
- 物理端到端延迟；
- 长期稳定性；
- 更多游戏/更多场景；
- 脱离 PC 的完整桥接；
- 原生 NS2 Pro 协议。

**最优先的三件事：**

1. 确认 11-16 的 `Pro Controller` 测试对象到底是不是飞智的 Switch USB 模式；
2. 把飞智直接插 NS2，确认 NS2 是否认它、是否发 `0x10`；
3. 用 NS2 Pro 在同一个场景做“主机到底有没有发原生震动”的判断。

## 1. 项目目的

在 Switch 2 的原生游戏里使用飞智八爪鱼 6 Pro，并把主机的触觉转成飞智音圈马达的震动。

目标链路：

```text
Switch 2
  → Pico 2W（模拟 NS Pro 一代，USB device）
  → Wi-Fi/UDP 或 PC
  → 解码/合成
  → 飞智接收器（37D7:2502，FFA0/MI02）
  → 飞智八爪鱼 6 Pro
```

约束：

- 不改主机、不改游戏；
- 不用游戏声音替代触觉；
- 不改飞智原厂持久配置；
- 不把“一代 Pro 兼容”说成“完整 HD Rumble 2”；
- 最终希望脱离 PC，做成独立硬件。

### 2.1 v043 的成功基线

| 项目 | 结果 |
|---|---|
| live 窗口 | 120 秒 |
| 启动总上限 | 180 秒 |
| 输入验收 | `1969/1969` |
| 游戏闭环 1 | `1107/1107` |
| 游戏闭环 2 | `1120/1120` |
| 组合验收 | 每轮 25 项 |
| 活动时长 | 约 120.067 秒 |
| 启用前输出 | 0 |
| 启用后提示 | 左右各一次 120ms / ±12 |
| 结束 | END2 `client_confirmed`，CRC/序号/配置通过 |
| v043 固件 SHA256 | `3f7df3484644560548917013a66caac2c7f4b6a4307768fbf377e3fb4e751f50` |
| 第15代完整快照 SHA256 | `48de32d41fc18a771bf4e5ab3254f9ce40aa3dfc052676fecc13f4bed6ec46fc` |

这是一条**受限提示映射**的成功基线：主机事件 → 120ms/±12 的提示包 → 飞智震动。  
它不是原始 HD 波形回放。

### 2.2 11-16 的 Switch USB 触觉记录

现场 JSON 的关键数据：

- 设备：`Pro Controller`，VID `0x057e`，PID `0x2009`；
- 声明的 output ID：`0x01 / 0x10 / 0x80 / 0x82`；
- 测试 pattern：左 400ms → 右 400ms → 两侧 400ms → 中性尾；
- `162/162` 帧写出，`replaced/failed` 为 0；
- dispatch 迟到：min `0.0027ms` / median `0.2981ms` / max `0.5894ms`；
- max write：`6.4146ms`；
- 对比轮：`312/312`，两轮 max write `5.5167ms` / `6.8602ms`；
- 左侧两次都比右侧钝，同一侧两次也不完全一致。

结论：

- 8ms 栅格 + 重叠写，可以把派发迟到压到 0.6ms 以内；
- `0x10` 在 Switch USB 模式下被接受，并能产生可分辨的左右输出；
- 手感差异更像设备特性，而不是传输/调度故障。

边界：

- 单一用户报告，无重复/盲测；
- 只发了一个 `LOW_160` 幅度/频率对；
- `WriteFile` 完成不等于手柄 ACK；
- 未证明波形保真。

> 待确认：JSON 只写 `Pro Controller`，提交正文说“native Switch USB haptics drive the Flydigi Apex 6 Pro”。  
> 最合理的解释是飞智在 Switch USB 模式下枚举成 Pro Controller；但需要确认测试对象，否则“飞智能解析 `0x10`”这个结论会站不稳。

### 2.3 实时性 campaign 的现状

11-15 的 60 秒硬件试次仍未通过：

- `165425` 试次：1 事件、859 帧、`6.872s`；
- 首次派发迟到 `6.6075ms`；
- 外层空档 `8.7016ms`；
- 62 代日志 1119 个源字段一致；
- 同步界面写盘移出主线程仍未解决；
- 4ms 逐帧门禁与 Windows 125Hz 调度现实不兼容。

离线缓解：

- 软件回放 60 秒单次通过；
- 自旋 2ms 把 1500 次派发压进 4ms（最坏 2.02ms，CPU 15.8%）；
- 但收包线程最坏 6.67ms；
- 4ms/80ms 保护没有放宽。

这批工作证明：**PC + Wi-Fi + Windows 调度不适合作为最终形态**，所以主线转向 Pico 独立 USB Host。

## 3. 当前问题

### 3.1 单 USB 控制器

Pico 2W 只有一个原生 USB 控制器。它不能同时：

- 对 NS2 做 USB device；
- 对飞智接收器做 USB host。

可选方案：

| 方案 | 判断 |
|---|---|
| PIO USB 再加一个 host | **推荐** |
| 蓝牙连飞智 | 基本堵死 |
| 第二块板/PC | 可行但违背“独立”目标 |

### 3.2 实时性

- PC 侧 64ms 缓冲；
- Wi-Fi 抖动 P95 约 38ms；
- Windows 125Hz 调度与 4ms 逐帧门禁冲突；
- RTT 不等于马达延迟。

### 3.3 保真

- 当前是“事件检测 → 120ms/±12 提示”，不是原始 `0x10` 回放；
- `1969/1969`、`1107/1107` 只证明收包字段一致，不证明输出波形；
- 飞智的“输入码 → 振动传递函数”还没有测；
- 11-16 只测了一个幅度/频率对；
- 左侧偏钝是设备特性，不能靠软件完全消除。

### 3.4 蓝牙

- 飞智 XInput 蓝牙模式不发 BLE 广播；
- 经典 BR/EDR 可以发现 `[设备蓝牙地址已隐去]`，CoD `0x0508`；
- ACL 建立后 20 秒无 L2CAP/SDP/认证；
- v4–v7 都在认证阶段返回 `0x05`；
- BLE 1020 条可连接广播中没有 Microsoft `0x0006`；
- Windows WPR 抓包被 `0x80070005` 拒绝，未取得 ETL。

结论：**不要把蓝牙当第一优先级。**

### 3.5 独立硬件

- v043 只有 `tinyusb_device`，没有 USB Host；
- 输入依赖 Windows XInputSource；
- 波形输出/解码/保护还在 Python；
- `standalone/receiver_probe` 只是静态库，不是固件；
- `standalone/bt_discovery` 已硬件验证，但 `bt_hid` 的 HOGP 方向已作废；
- PIO USB 双角色还没验证。

## 5. 三条路线

### 路线 A：先用 PC 验证 HD 参数（最快）

不改硬件，只改 PC 输出：

```text
Pico 记录：seq + left4 + right4 + timestamp
PC 原样塞进 0x10：不改时长、不改幅度、不做事件映射
```

目的：回答“飞智到底认不认这 4 字节”。

测试矩阵：

- 左 / 右 / 两侧；
- 80 / 160 / 320 / 640 / 1000Hz；
- 幅度 0.2 / 0.4 / 0.6 / 0.8；
- 每段 200ms；
- 固定 8ms；
- 每段后回中性 `00 01 40 40`。

### 路线 B：PIO USB 脱机（最终形态）

```text
NS2
  → Pico 原生 USB（Pro 1 device）
  → Pico 板上处理
  → PIO USB（飞智接收器 host）
  → 飞智接收器
  → 手柄
```

第一个里程碑只要：

1. PIO USB 枚举到 `37D7:2502`；
2. 读到 receiver 的 HID 描述符/输入报告；
3. 发一个中性输出；
4. 发一个固定震动报告，确认手柄震；
5. 先不转发输入。

工具：

- [Pico-PIO-USB](https://github.com/sekigon-gonnoc/Pico-PIO-USB)；
- 原生 USB 继续做 NS2 device；
- 关闭 Wi-Fi/CYW43；
- 调试走 UART，不占用原生 USB 做 CDC；
- 接收器 5V 从 Pico VBUS 或外部 5V 供，共地；
- D+/D- 按示例接，串 22Ω 更好。

### 路线 C：蓝牙（不建议先做）

只有当前两条都卡住时再考虑。现有证据已经表明经典 HID 认证和 BLE 广播都不顺。

## 6. 推荐测试顺序

### Phase 0：今天就能做，不需要新硬件

1. **飞智 Switch USB 直插 NS2**
   - NS2 是否识别？
   - 按键/摇杆是否正常？
   - 游戏里是否有震动？
   - 如果这条通了，可能大幅简化甚至绕过桥接。

2. **飞智接收器直插 NS2**
   - NS2 是否识别 `37D7:2502`？
   - 如果识别，先测原生震动；大概率不识别。

3. **NS2 Pro 同场景对照**
   - 同一个游戏、同一个事件；
   - NS2 Pro 震不震？
   - 如果 NS2 Pro 不震，当前 120ms 很可能只是项目自己合成的提示，不是复刻主机 HD。

### Phase 1：PC 链路 raw passthrough

- 先确认飞智对 4 字节的真实响应；
- 再做传递函数/预失真；
- 不要先做 PIO USB，否则可能白做。

### Phase 2：PIO USB 脱机

- 枚举接收器；
- 固定震动；
- raw `0x10` 透传；
- 输入转发；
- 最后才是完整 standalone。

### Phase 3：保真与稳定性

- 参数/8ms 节奏；
- 起振/停振约一帧内；
- 幅度单调；
- 主频趋势；
- 左右差异；
- 盲测 ABX；
- 更多游戏/长时间运行。

## 8. 风险与判断

- 如果飞智 Switch USB 模式能在 NS2 上直接工作，项目范围可能大幅缩小；
- 如果只能在 PC 上工作，NS2 可能还有认证/枚举差异，不能想当然；
- 如果飞智只支持少数档位/频率，软件预失真上限很低，最终要考虑独立 LRA 驱动；
- PIO USB + 原生 USB device 的共存需要先做最小验证，不能直接排期全链路；
- 蓝牙路线成功概率低，不建议先投入；
- NS2 Pro 只能做主观参考和“是否发震动”的指示器，不能做客观测量。

## 10. 术语

- **Pro 1 / NS Pro 一代**：Switch 1 的 Pro Controller 协议；Pico 目前模拟它。
- **HD Rumble**：Pro 1 的 4 字节频率/幅度参数，8ms 更新。
- **HD Rumble 2**：Switch 2 Pro 手柄的新触觉，协议未公开。
- **`0x10`**：Pro 1 的 rumble-only 输出报告。
- **raw passthrough**：不改参数，原样转发。
- **事件提示**：当前项目的 120ms/±12 合成包，不是原始回放。
- **PIO USB**：用 PIO 模拟第二个 USB 控制器，解决单 USB 口不能同时 device+host 的问题。
